# 提交规范

本规范面向在本仓库提交代码的 AI agent（也适用于人）。CI 会用 `scripts/check-commit-msg.sh` 检查 PR 里的每条提交和 PR 标题。

## 1. 格式

采用 [Conventional Commits 1.0](https://www.conventionalcommits.org/zh-hans/v1.0.0/)：

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **标题**（第一行）必填，总长不超过 72 个字符。
- `type`、`scope` 只能用下面列出的英文关键字，全部小写。
- `scope` 可省略；一次提交确实跨多个 scope 时用逗号分隔，不加空格：`fix(exec,ui): ...`。超过两个 scope 通常说明应该拆成多个提交。
- 冒号后恰好一个空格。
- **subject 用英文祈使句**，首字母小写，结尾不加句号：`add pipeline model`，而不是 `Added pipeline model.`。专有名词保持原样（`Windows`、`SFTP`）。
- **正文可用中文或英文**，与标题之间空一行，每行建议不超过 100 个字符。正文写“为什么改”和“改了什么不显而易见的东西”，不要复述 diff。

## 2. type

| type | 用途 |
| --- | --- |
| `feat` | 新功能（用户可感知的能力） |
| `fix` | 修复缺陷 |
| `refactor` | 不改变行为的重构 |
| `perf` | 性能优化 |
| `test` | 只增改测试 |
| `docs` | 只改文档（含 `docs/` 下的需求、设计、计划） |
| `style` | 只改格式（rustfmt、prettier），不改逻辑 |
| `build` | 构建系统、依赖清单、打包配置（Cargo.toml、package.json、tauri.conf.json） |
| `ci` | GitHub Actions 与检查脚本 |
| `chore` | 其他杂项（.gitignore、工具配置） |
| `revert` | 回滚某个提交 |

## 3. scope

scope 对应代码所在位置（路径相对 `MyDeployMate-Tauri/`）：

| scope | 位置 |
| --- | --- |
| `core` | `crates/core`：领域模型、校验、变量解析、任务展开、状态机 |
| `store` | `crates/store`：workspace.json、备份、导入导出、SQLite 历史 |
| `exec` | `crates/exec`：本地执行、SSH、SFTP、sudo、主机信任、调度器 |
| `tauri` | `src-tauri`：Tauri 命令、事件、窗口、打包配置 |
| `ui` | Vue 前端（`src/`）：页面、组件、Pinia store、路由 |
| `design` | `design/`：设计令牌与视觉规范 |
| `spike` | `spikes/`：阶段 0 技术验证代码 |
| `test-env` | `test-env/`：Docker SSH 测试环境 |
| `demo` | `demo/`：原交互原型 |
| `deps` | 只升级或调整依赖版本（常与 `build` 搭配：`build(deps): ...`） |
| `repo` | 仓库根目录的配置与说明（AGENTS.md、.gitignore、scripts/） |

只改 `docs/` 时一般用 `docs` type 且不写 scope；文档只涉及某一模块时可写该模块的 scope，如 `docs(exec): ...`。

需要新 scope（比如新增了一个 crate）时，在同一个 PR 里同时修改本表和 `scripts/check-commit-msg.sh` 里的 `SCOPES`。

## 4. 破坏性变更

改变 workspace.json 结构、导入导出格式、Tauri 命令签名等不兼容的变更，在 type/scope 后加 `!`，并在 footer 写明迁移方式：

```
feat(store)!: rename pipeline steps field

BREAKING CHANGE: schemaVersion 升到 3，旧文件由 migrate_v2_to_v3 自动迁移。
```

## 5. footer

- 关联需求或验收编号：`Refs: SRV-01, AC-08`（编号来自 `docs/软件需求规格说明书.md`）。
- 关闭 issue：`Closes #12`。
- 运行环境要求的署名行（如 `Co-Authored-By:`）放在 footer 最后。

## 6. 提交粒度

- 一个提交只做一件事，能独立通过 `cargo fmt --check`、`cargo clippy -- -D warnings`、`cargo test` 和前端检查。
- 格式化、重命名这类机械改动单独提交，不和逻辑改动混在一起。
- 不要提交 `fixup!`、`squash!`、`wip` 之类的临时提交；合并前用 rebase 整理掉。
- 不提交构建产物、`node_modules`、密钥、私钥或真实服务器地址。

## 7. 示例

```
feat(core): validate server host and port fields

按 SRV-01 校验主机名、IPv4/IPv6 和端口范围，错误带对象路径，
例如 servers[2].port。

Refs: SRV-01, AC-08
```

```
fix(exec): kill whole process tree on cancel

之前只终止了直接子进程，npm 拉起的 node 进程会残留。
改为把子进程放进 Job Object，取消时关闭 Job。

Refs: RUN-05
```

```
build(deps): bump russh to 0.64.1
```

```
ci: add Windows clippy and test job
```

错误示例：

| 写法 | 问题 |
| --- | --- |
| `Add pipeline model` | 缺少 type |
| `feat(pipeline): add model` | `pipeline` 不是允许的 scope，应为 `core` |
| `feat(core): Added pipeline model.` | 用了过去时、首字母大写、结尾句号 |
| `fix(core):修复校验` | 冒号后缺空格，subject 应为英文 |
| `update` | 没有任何信息 |

## 8. 本地检查

```bash
# 一次性启用提交钩子，之后每次 git commit 都会自动检查
git config core.hooksPath .githooks

# 手动检查当前分支相对 main 的所有提交
scripts/check-commit-msg.sh --range origin/main HEAD

# 检查一条标题（比如 PR 标题）
scripts/check-commit-msg.sh --title "feat(core): add pipeline model"
```

使用 squash 合并时，PR 标题会成为 main 上的提交标题，所以 PR 标题也要遵守第 1 节的格式。
